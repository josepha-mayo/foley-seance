# Bounded timed door prototype: provenance and limits

This extension is integrator-authored, not newly generated by Kiro. It extends the existing Kiro-origin DSP engine while retaining its prior provenance.

An isolated Kiro CLI attempt on the authorized Windows computer on 2026-11-17 requested a pure door-envelope helper and tests, using the existing CLI workflow. It exited 1 with: `Not logged in. Set the KIRO_API_KEY environment variable or run kiro-cli login first.` No generated code was obtained or used. No credentials were read and no sign-in or desktop takeover was performed. Continued implementation was authorized as an integrator extension.

## Contract

Recipe version 3 requires `echoAmount` and exactly one `doorEvent: { at }`, where `at` is a finite source fraction in [0, 1). The existing `doorClosed` is the initial state. At the event time, a linear 150 ms transition toggles this state, shortened to the remaining source duration if needed. The final state is held through the tail. A compiled envelope snapshots input; `doorClosedAmount` exposes the same timing for visuals. Unsupported or malformed event data is rejected.

No-event recipes remain versions 1 and 2 with their original arithmetic branches. These are not automatically migrated. The event interpolates the existing artistic gain and low-pass coefficient. Existing delay-line history persists across a transition; this is not a physical door/room simulation or a full re-filtering of earlier ambience. Global peak normalization can rescale the whole cue when necessary, as before.

## Core verification

- 192 engine tests passed, including ten new timed-event tests.
- 48 independent comparisons against the sealed first-view1 renderer produced identical WAV bytes: two sample rates, three built-in sources, both initial door states, version 1 and version 2 echo amounts 0, 0.3 and 0.6.
- Event tests cover exact pre-event PCM equality to the initial static door on a low-level source (no global limiting), changed output afterward, both transition directions, shortened ramps, one-sample input, tail envelope state, zero/nonzero echo, repeatability and exported PCM/preview identity.
- These are automated numerical/contract checks, not a listening evaluation. No claim of click-free perception, acoustic realism, creator preference or competitive novelty follows from them.
- This core prototype has not by itself qualified UI behavior, project persistence, native browser rendering, Windows installation, or a production release. Those are integration responsibilities.
